## Video feed and administration

The public feed in `index.html` reads documents from the Firestore `videos` collection where `admin` is `"yes"`. Each document uses its Firestore document ID as the video ID and supports these fields:

- `link`: Cloudinary video URL
- `mediaType`: `"video"` or `"image"`; older documents without this field are treated as videos
- `description`: video caption
- `likesCount`, `savesCount`, `sharesCount`: numeric counters
- `comments`: array of comment strings or comment objects; comment objects may include `username`, `userId`, `text`, and `profileImageLink`
- `uploadedBy`: creator name
- `username`, `userId`: the creator's reserved username and profile ID
- `profileImageLink`: Cloudinary profile-image URL
- `admin`: `"yes"` to include the video in the public feed

## Superadmin

Open `superadmin.html` to upload and manage media, user profiles and balances, the new-account coin bonus, and website activity. The sign-in page compares the entered `username` and `password` with the `admin/login` Firestore document. Admin uploads saved as drafts use cloud `hjkjnzpz` and preset `pending_review`; publishing transfers those assets to cloud `s35mxosr` using preset and folder `user_uploads`. Admin uploads published immediately go directly to the publishing cloud.

The admin page requires a creator username when adding or editing a video. It reuses an existing username or creates and reserves Firestore `users` and `profiles` records for a new creator, and saves the creator's `userId` and username on the video. This creates profile records only, not a Firebase Authentication account. The admin page manages every field listed above, including counters, comments, and published/draft visibility. Its Users tab lists follower/following totals, allows editing all fields in a user's private document, and provides a verification toggle. Verification is stored as `"yes"` or `"no"` in both `users/{uid}` and `profiles/{uid}`; public badges read the public profile value. The raw user-field editor represents Firestore timestamps with a `$firestoreTimestamp` ISO-date marker. Deleting a video removes its Firestore document; the unsigned Cloudinary configuration cannot delete the uploaded asset. Its credential check runs in the browser and is only a UI gate; it does not secure Firestore. Do not rely on it for authorization. Protect the database with restrictive Firestore Security Rules and a server-enforced authentication design before using it with sensitive or production data.

## User accounts and feed activity

Users can browse and scroll the public feed without an account. Liking is also available while signed out; comments and other feed actions send users to `oauth.html` to log in or register. Email/password authentication must be enabled in Firebase Authentication. Registration stores private account details (including email and phone) in `users/{uid}`, creates a public profile at `profiles/{uid}`, and reserves lowercase usernames in `usernames/{usernameLower}`. Public profiles contain `fullName`, `username`, `usernameLower`, `profilePic`, `bio`, and `pinnedVideos`; liked/saved video IDs are stored on the owner's private user document. Signed-in users can upload photos or videos from their device or capture media from a camera in the create modal. Submissions upload to cloud `hjkjnzpz` using preset `pending_review`, then save in `videos` as drafts (`admin: "no"`) with zero counters and the user's username/profile picture.

The signed-in `wallet.html` page displays the user's `earningsBalance` and `availableBalance`, both in coins, and links to `buy-coins.html` and `withdraw-coins.html`. New-user balances initialize to zero earnings and the configured welcome bonus as available coins (zero when no bonus is configured). Superadmin manages the integer coin bonus in `admin/newUsers.bonus`, and can edit individual user balances from the Users editor. When a nonzero bonus is issued during registration, the transaction writes an `activities` record with action `welcome_bonus`, amount and coin currency; the inbox displays it under Activity. Firestore rules must allow signed-in users to read the non-sensitive `admin/newUsers` settings document and restrict its writes to a trusted admin/server.

`buy-coins.html` offers crypto and P2P deposits. Superadmin configures enabled crypto payment entries and merchants in `admin/coinPayments`; crypto entries include the rate per coin, network, address, optional QR image URL, and instructions. Merchant entries include an admin-uploaded profile picture, coin inventory and order limits, payment method (`Bank transfer` or `MoMo transfer`), and payment instructions. Merchant pictures are uploaded to Cloudinary and saved as the merchant's `profilePic` URL. Users submit an image/PDF proof to `coinDeposits`; requests stay pending until review. Approval credits `users/{uid}.availableBalance` transactionally, deducts approved P2P coins from the merchant inventory, and records `coin_purchase` in `activities`. Submissions and rejections also create user activity records.

Verified users can transfer earnings to their available balance from `wallet.html`; this updates both balances atomically and logs a `coin_transfer` activity. `withdraw-coins.html` lets verified users request crypto, MoMo, or bank withdrawals. Admin configures method/currency payout rates in `admin/withdrawalSettings.rates`. A pending request reserves its coin amount from `availableBalance`; admin approval marks it paid, while rejection refunds the reserved coins. Submission, approval, and rejection are written to `activities`. The Coins & wallet section in `superadmin.html` has subtabs for welcome bonuses, crypto methods, merchants, coin purchase requests, withdrawal rates, and withdrawals. Crypto QR images can be uploaded in the admin panel, which fills the saved image URL. The superadmin sign-in remains a browser-side UI gate: production authorization must enforce admin-only approvals and configuration writes with trusted server code and restrictive Firestore Security Rules; do not permit users to change balances or approve their own requests.

The profile header's right-side menu opens the account sidebar with Wallet, Activity center, Your QR code, Boost and Ads, Settings and privacy, and Log out. The activity center reads the signed-in user's `activity` records for playback, comments, searches, and wallet events. Submitted searches are saved with action `search` and the term in `details.term`. Your QR code links to `view-profile.html?uid={uid}`. `settings.html` lets the signed-in user view and update only their email, phone number, date of birth (`dateOfBirth`), and country (ISO country code) in `users/{uid}`; changing the authentication email may require a recent sign-in. Back-arrow controls use browser history to return to the previous page.

When an admin publishes a creator draft, the source image or video is copied to cloud `s35mxosr` using preset and folder `user_uploads`; Firestore is updated to the new URL and the video is published only after transfer succeeds. Cloudinary assets uploaded to the review cloud are not automatically deleted after transfer.

Feed interactions are recorded as documents in `activity` with `videoId` and/or `profileId` when relevant, `userId`, `action`, `details`, and `createdAt`. Profile visits are recorded for the profile owner's viewer list. Follow relationships are stored in `follows` documents keyed by follower/followed user IDs, with `followerId`, `followingId`, and `createdAt`; follow and unfollow actions are also recorded in `activity`. Profile follower/following totals are computed from these relationship documents. Profile likes total the `likesCount` values of the user's published videos. Public profile pages query videos with `admin == "yes"` and then select the requested creator's posts, so Firestore rules must allow public reads of published videos and public profiles; allow follow-document reads if public follower counts are required. Likes, saves, and shares update `likesCount`, `savesCount`, and `sharesCount` on the corresponding `videos/{videoId}` document; signed-in likes/saves also update the owner's private ID lists. Comments include the author's username, user ID, and profile picture; opening a commenter with a stored username leads to `view-profile.html?username=…`. A commenter without a username is shown as profile locked. Creator verification badges appear in feed posts, comments, profile pages, and the profile video viewer when `profiles/{uid}.verify` is `"yes"`. When admins save video comments, usernames are checked against `users`; missing commenters are created as Firestore user/profile documents and their usernames are reserved, with the video and commenter records committed together. Admins can edit comments and upload commenter profile images, and manage public user profile details and images in `superadmin.html`. The admin dashboard also displays the latest 100 activity records. Profile video cards open a full-screen, vertical snap-scrolling viewer. Signed-out likes use a locally generated guest identifier. Configure Firestore Security Rules to restrict follow creation/deletion to the authenticated follower; validate activity writes and counter changes; reserve usernames safely; and restrict `users` documents to their owner. Client-side UI checks are not authorization.

The signed-in inbox shows the latest activity preview above direct messages and opens an “Activity & new followers” modal. It reads user-relevant feed activity from `activity` (and `activities` for compatibility), and displays current followers from `follows`. Direct messages support text, image, and video attachments plus recorded voice notes; uploaded chat media uses the `hjkjnzpz` Cloudinary cloud and `pending_review` unsigned preset. `search.html` searches public profiles and published video/photo descriptions, keeps recent searches in local storage, and opens matching media in the profile video viewer. The feed’s Following tab filters published videos to creators the signed-in user follows. Unread conversation badges are shared across the feed, search, inbox, friends, profiles, and direct-message screens.

## Activity rewards, promotions, and verification

`superadmin.html` → Growth & verification configures per-action coin rewards in `admin/activityRewards` (`like`, `comment`, `share`, `watch`), per-unit promotion prices in `admin/boostSettings` (`likes`, `followers`, `videoViews`, `profileViews`), and the verification fee in `admin/verificationSettings.fee`. Successful signed-in feed likes, comments, shares, and video watches credit the acting user's `users/{uid}.earningsBalance`; a matching `activities` system record (`activity_reward`) appears in the recipient's inbox when a positive reward is credited. Unlikeing does not remove previously earned coins. A signed-in user earns a watch reward only once per video, enforced by `users/{uid}/watchedVideos/{videoId}` inside the same Firestore transaction that records playback in `activity`. Rewatching records watch history but does not credit coins again. Playback in the feed and the shared profile/search video viewer uses this same transaction helper.

Verified users can submit promotion requests from `boosts-and-ads.html`. They choose a promotion goal and integer quantity; likes and video-view requests target one of their published videos. The total is debited from `availableBalance` transactionally, and the request is stored in `boostRequests` with `status: "pending"`. The admin panel can mark a campaign fulfilled or reject it and refund the coins. The site queues these requests for manual fulfillment; it does not artificially increment likes, follower, or view counts. Unverified users can submit one pending request from `verify-account.html`; the configured fee is charged from available balance and stored in `verificationRequests`. Admin approval sets `verify: "yes"` on both the private account and public profile; rejection refunds the fee. Request and review events are saved to `activities` and shown in the inbox.

The reward, promotion, and verification transactions run in client-side Firebase code. The superadmin credential check remains a browser-side UI gate and is not authorization. Before production, enforce admin-only configuration/reviews and server-validated balance changes, reward rates, request states, and ownership with restrictive Firestore Security Rules and trusted server code. Never allow a client to award itself arbitrary earnings or approve/refund its own requests.
